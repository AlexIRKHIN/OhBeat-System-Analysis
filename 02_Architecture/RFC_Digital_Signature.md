# ⚖️ RFC: Модуль юридической фиксации прав (ПЭП по 63-ФЗ)

Договор на передачу эксклюзивных прав (Exclusive) подписывается одноразовым кодом до оплаты, а на остальные неисключительные лицензии — акцептом оферты. Обе стороны заранее принимают соглашение об использовании простой электронной подписи (ПЭП), без которого подпись не признается равнозначной собственноручной. 

---

## 1. Правовое обоснование и цель

* ПЭП признается равнозначной собственноручной подписи, если это предусмотрено соглашением между участниками электронного взаимодействия ([ч. 2 ст. 6 63-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_112701/)). Соглашение принимают обе стороны: Продюсер — при подключении к продажам, Артист — при регистрации. Факт принятия пишется в неизменяемый Audit Log.
* Лицензионный договор заключается в письменной форме (п. 2 ст. 1235 ГК РФ). Электронный документ, подписанный по соглашению сторон, соответствует письменной форме (п. 2 ст. 160 ГК РФ).

**Цель модуля:** Придать генерируемым PDF-договорам полную юридическую силу, не добавляя лишних шагов и трения в процесс покупки обычных неисключительных лицензий.

---

## 2. Механизм подписания по типам лицензий

| Лицензия | Механизм | Чем подтверждается | Момент подписания |
| :--- | :--- | :--- | :--- |
| **Basic, Premium, Trackout** | Акцепт публичной оферты (п. 3 ст. 438 ГК РФ) из авторизованной сессии | Учетная запись + отметка в чекбоксе + успешная оплата | Чекбокс — перед переходом к оплате |
| **Exclusive** | Подписание договора ПЭП с одноразовым кодом | 6-значный код по SMS (или email, если телефона нет) | До создания платежа (`428 SIGNATURE_REQUIRED` без подписи) |

> **Параметры безопасности OTP:** Для подтверждения используется 6-значный код. При ограничении в 3 попытки шанс подобрать код перебором составляет 0,0003%. Срок жизни кода — 5 минут с учетом возможных сетевых задержек доставки SMS-шлюза.

---

## 3. Флоу подписания Exclusive



1. **Оферта Продюсера:** При подключении к продажам Продюсер принимает соглашение о ПЭП и типовые условия лицензий. Публикуя бит с активной лицензией Exclusive, он делает юридически значимое предложение заключить договор на этих условиях. 
2. **Запрос кода:** Артист нажимает «Подписать». Система собирает текст договора с данными сторон, вычисляет SHA-256 от текста проекта (`draft_sha256`) и отправляет OTP-код.
3. **Проверка кода:** Артист вводит код. Система сверяет хэш кода, число попыток и срок жизни (согласно [NFR-31](../01_Requirements/FR_NFR.md)), затем фиксирует подпись в таблице `contracts` и Audit Log: телефон/email, IP-адрес, точное время, `draft_sha256`.
4. **Оплата:** Договор вступает в силу исключительно с момента оплаты. Если оплата не прошла или отменена, подписанный проект остается без юридических последствий.
5. **Финальный PDF:** После события `payment.succeeded` система генерирует итоговый PDF-договор со штампом ПЭП обеих сторон, вычисляет его хэш (`pdf_sha256`) и сохраняет файл в приватный бакет S3.

**Почему используются два разных хэша:**
* `draft_sha256` доказывает, под каким именно текстом Артист поставил подпись с помощью кода.
* `pdf_sha256` доказывает, что выданный покупателю итоговый файл не изменялся после генерации. Хэш PDF нельзя впечатать внутрь самого PDF (так как вставка изменит сам хэш), поэтому он хранится в базе данных и выводится в разделе «Мои покупки» для сверки.

## 4. API подписания

| Метод и URI | Тело запроса | Возможные ответы |
| :--- | :--- | :--- |
| `POST /v1/orders/{id}/signature/otp` | `{ "channel": "sms" }` | `202 Accepted` — `{ "expires_at", "resend_after" }`<br>`429 TOO_MANY_REQUESTS` — исчерпан лимит отправок |
| `POST /v1/orders/{id}/signature/verify` | `{ "code": "583204" }` | `200 OK` — `{ "signed_at" }`<br>`400 INVALID_CODE` — `{ "attempts_left" }`<br>`410 CODE_EXPIRED` — код истек, запросите новый |

## 6. Хранение данных подписи

Так как один заказ может содержать несколько битов от разных продюсеров, лицензионный договор заключается на каждую позицию заказа (order item) отдельно. Сущности подписи строго нормализованы (см. [Физическую модель данных](../05_Database/Database_Schema.md)):

* **Таблица `contracts`:** Хранит атрибуты `signature_type` (`offer_accept` или `otp`), `draft_sha256`, `pdf_sha256`, ключ объекта `pdf_key`, `signer_ip` и метку времени `signed_at`.
* **Таблица `signature_otps`:** Хранит транзитные данные сессий подписания — канал отправки (`channel`), хэш кода (`code_hash`), счетчик попыток (`attempts`), время истечения (`expires_at`) и время успешного подтверждения (`confirmed_at`).
