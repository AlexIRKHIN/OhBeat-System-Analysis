# 🎵 Архитектурное решение: стриминг аудиопревью (HTTP Range Requests)

Превью воспроизводится стандартным HTML5-элементом `<audio>`, а распределенная сеть доставки контента (CDN) и объектное хранилище S3 отдают файл частями по HTTP Range-запросам со статусом `206 Partial Content`. Браузер самостоятельно запрашивает нужный диапазон байтов при старте и перемотке, поэтому собственная серверная реализация нарезки на чанки не требуется.

---

## 1. Контекст и бизнес-проблема

Артисты при прослушивании каталога обычно оценивают первые секунды трека либо сразу перематывают воспроизведение к припеву или дропу.

Если при каждом клике скачивать превью целиком стандартным запросом:
* **Неэффективный расход трафика:** Платформа оплачивает исходящий трафик CDN за те части файла, которые пользователь даже не дослушал (особенно критично при быстром перелистывании треков).
* **Задержка старта (Latency):** На нестабильном мобильном интернете воспроизведение начинается с ощутимой паузой, пока файл буферизируется целиком.
* **Проблемы с перемоткой:** Переход в середину еще не загруженного трека блокирует воспроизведение.

### Инженерные цели
* Старт воспроизведения звука **быстрее 300 мс** для 75% запусков (метрика p75) при попадании в кэш CDN.
* Мгновенная произвольная перемотка дорожки без необходимости скачивать весь файл заново.
* Расход исходящего трафика строго пропорционален фактически прослушанному фрагменту аудио.

## 2. Архитектурное решение

1. **Формат медиафайла:** Для каждого бита фоновый воркер генерирует один MP3-файл с битрейтом 128 кбит/с и циклично наложенным войстегом продюсера, после чего загружает его в публичный бакет S3 за CDN (FR-10, FR-11).
2. **Версионирование и долгосрочный кэш:** Имя файла содержит суффикс версии (например, `112233_v1.mp3`). При замене файла версия инкрементируется, что позволяет кэшировать объект на CDN и в браузере на один год с заголовком `Cache-Control: public, max-age=31536000, immutable`.
3. **Обслуживание диапазонов на CDN:** Edge-сервер CDN кэширует объект целиком и самостоятельно отвечает на побайтовые HTTP Range-запросы клиентских устройств, отдавая только запрошенные сегменты.
4. **Спецификация:** Механизм частичной отдачи данных реализован строго по спецификации [RFC 9110 (раздел 14)](https://www.rfc-editor.org/rfc/rfc9110#section-14).

## 3. Сетевой протокол и HTTP-взаимодействие

### 3.1. Старт воспроизведения (запрос с начала)
Браузер запрашивает файл с нулевого байта открытым диапазоном и начинает наполнять внутренний буфер воспроизведения.

**Request:**
```http
GET /previews/112233_v1.mp3 HTTP/1.1
Host: cdn.ohbeat.com
Range: bytes=0-
```

**Response:**
```http
HTTP/1.1 206 Partial Content
Content-Type: audio/mpeg
Content-Range: bytes 0-2943999/2944000
Content-Length: 2944000
Accept-Ranges: bytes
Cache-Control: public, max-age=31536000, immutable
```

> **Пояснение данных:** Файл объемом 2 944 000 байт при битрейте 128 кбит/с соответствует 184 секундам звучания. Заголовок `Content-Range` сразу сообщает клиенту полный размер файла, что позволяет плееру корректно рассчитать шкалу длительности и смещение для перемотки.

### 3.2. Перемотка на середину трека
При клике пользователя на середину трека браузер прерывает активное чтение первого диапазона и отправляет новый запрос со смещением.

**Request:**
```http
GET /previews/112233_v1.mp3 HTTP/1.1
Host: cdn.ohbeat.com
Range: bytes=1472000-
```

**Response:**
```http
HTTP/1.1 206 Partial Content
Content-Type: audio/mpeg
Content-Range: bytes 1472000-2943999/2944000
Content-Length: 1472000
Accept-Ranges: bytes
```

## 4. Спецификация поведения клиентского плеера (Frontend)

* **Ленивая загрузка (`preload="none"`):** В карточках каталога плеер инициализируется без предварительной подгрузки аудио. До физического нажатия кнопки Play сетевой трафик не расходуется.
* **Нативная буферизация браузера:** Глубина буфера определяется встроенным медиастеком браузера с учетом скорости сети (кастомный контроллер чанков не используется, так как стандартный элемент `<audio>` не имеет API для ручной регулировки размера буфера).
* **Корректный разрыв соединения:** При переключении на другой бит плеер вызывает `pause()`, удаляет атрибут `src` (`audio.removeAttribute('src')`) и вызывает метод `load()`. Это принудительно останавливает фоновое скачивание предыдущего трека.
* **Кэширование на клиенте:** Уже полученные побайтовые диапазоны сохраняются в кэше браузера и при повторном воспроизведении трека не запрашиваются из сети повторно.

## 5. Анализ отвергнутых альтернатив

| Технология | Причина отказа для OhBeat |
| :--- | :--- |
| **Кастомные чанки через `fetch()` + Media Source Extensions (MSE)** | MSE не поддерживается в мобильном Safari на iOS 15, что нарушает обязательное системное требование совместимости NFR-18. |
| **HLS (HTTP Live Streaming) / DASH** | Требует отдельного этапа нарезки файлов на `.ts`-сегменты и поддержки плейлистов `.m3u8`. Для коротких превью (2–4 минуты) архитектурная сложность избыточна. |
| **Скачивание файла целиком (`200 OK`)** | Создает перерасход сетевого трафика за непрослушанные секунды и дает долгий отклик на мобильных устройствах. |

---

## 6. Валидация эффективности решения

Эффект от использования HTTP Range Requests верифицируется в продакшене по двум системным метрикам:
1. **Экономия трафика CDN:** Отношение объема фактически отданных байтов к расчетному объему (произведение количества запусков плеера на полный размер файла).
2. **Задержка старта:** Разница во времени между событием пользовательского клика по кнопке Play и возникновением события медиаэлемента `playing`.
